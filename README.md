Ниже суть системы в собранном виде.

## Что это за система

Это **интеллектуальная система автоматической проверки студенческих работ**, где основой выступает **база знаний**.
Её назначение — принять документ студента, понять **что это за тип работы**, **к какому семестру она относится**, **какие требования к ней применяются**, затем **проверить документ по этим правилам** и выдать **понятный отчёт с нарушениями и рекомендациями**.

Это прямо совпадает с темой и целями пояснительной записки: разработка базы знаний для системы автоматизации проверки студенческих работ, работа с DOCX/PDF, извлечение текста, применение правил, выявление нарушений и формирование результатов анализа.  

## Как система должна работать по шагам

### 1. Пользователь загружает документ

Студент или преподаватель через интерфейс загружает файл.

Поддерживаются как минимум:

* `DOCX`
* `PDF`

Это соответствует постановке проекта: система должна работать с электронными документами этих форматов. 

### 2. Система извлекает содержимое документа

После загрузки документ попадает в модуль обработки:

* читается текст;
* при необходимости извлекаются заголовки, разделы, таблицы, подписи, список литературы;
* отдельно могут извлекаться метаданные: шифр работы, название, дисциплина, год, группа, автор.

### 3. Определяется тип документа

Система должна понять, что именно загружено:

* пояснительная записка;
* курсовой проект;
* лабораторная работа;
* отчёт;
* другой учебный документ.

В вашей модели это один из базовых этапов анализа. В самой записке также указано, что одной из задач базы знаний является **классификация документа** и выбор соответствующего набора правил. 

### 4. Определяется семестр документа

Дальше система должна определить, **под какой семестр подходит документ**.

Логика здесь такая:

* база знаний хранит признаки семестровых шаблонов;
* система сравнивает загруженный документ с этими признаками;
* выбирает наиболее подходящий семестр.

Для вашего примера это особенно важно, потому что у вас есть шаблон пояснительной записки **в 4 семестре**, и система должна уметь распознавать такие признаки. В загруженном шаблоне на титуле прямо указан код `КП4`, что фактически является сильным признаком 4 семестра. 

То есть модуль определения семестра может опираться на:

* шифр документа;
* структуру разделов;
* шаблон титульного листа;
* формулировки задания;
* состав обязательных разделов;
* правила конкретной кафедры.

### 5. Из базы знаний выбираются нужные правила

После определения:

* типа документа,
* семестра,
* возможно кафедры/дисциплины,

система достаёт из базы знаний **ровно тот набор требований**, который подходит этому документу.

Это соответствует идее из записки: база знаний должна хранить правила оформления, ограничения, параметры проверки, разные наборы правил для разных типов работ и поддерживать их обновление без изменения кода. 

## Что должно храниться в базе знаний

По сути база знаний — это не просто список текстов, а формализованное хранилище правил.

Она должна содержать:

### Декларативные знания

Что должно быть в документе:

* титульный лист;
* задание;
* содержание;
* введение;
* разделы;
* заключение;
* список источников;
* приложения.

### Структурные знания

Как устроен документ:

* какие разделы обязательны;
* в каком порядке они идут;
* какие разделы могут быть вложенными;
* какие элементы относятся к конкретному типу работы.

### Процедурные знания

Как проверять:

* если отсутствует обязательный раздел — фиксировать нарушение;
* если заголовок оформлен неверно — фиксировать нарушение;
* если структура не совпадает с шаблоном семестра — снижать уверенность определения.

### Знания об ограничениях

Конкретные нормативы:

* допустимые шрифты;
* интервалы;
* поля;
* оформление списков;
* требования к рисункам, таблицам, литературе;
* допустимые диапазоны объёма.

### Интерпретационные знания

Как объяснять результат:

* текст ошибки;
* критичность;
* рекомендация по исправлению;
* ссылка на нарушенное правило.

Это почти полностью совпадает с формулировками разделов 1.5–1.6 в записке. 

## Какой должна быть минимальная рабочая версия

Минимально готовое решение должно делать не всё подряд, а только базовый рабочий цикл.

### MVP

1. Загрузка `PDF/DOCX`
2. Извлечение текста и структуры
3. Определение:

   * типа документа
   * семестра
4. Проверка нескольких обязательных требований
5. Вывод отчёта

### Что проверить в MVP

Например:

* есть ли титульный лист;
* есть ли содержание;
* есть ли введение;
* есть ли заключение;
* есть ли список источников;
* совпадает ли структура с шаблоном;
* соответствует ли документ шаблону 4 семестра;
* найден ли код вроде `КП4`.

## Какую роль играют нейросеть, RAG и графовая БЗ

У вас по контексту фигурируют три уровня.

### 1. База знаний

Это основа системы.
Она хранит правила, связи, шаблоны, признаки типов документов и семестров.

### 2. Графовая база знаний

Нужна, если хотите показать более интеллектуальную архитектуру:

* `Документ` связан с `Типом документа`;
* `Тип документа` связан с `Требованиями`;
* `Семестр` связан с `Шаблонами`;
* `Нарушение` связано с конкретным правилом;
* `Отчёт` формируется на основе найденных нарушений.

Граф здесь уместен, потому что у вас много сущностей и связей между ними.

### 3. RAG

RAG нужен, если система должна не просто проверять жёсткие правила, а ещё:

* подтягивать фрагменты методички;
* находить релевантные требования;
* объяснять, почему правило нарушено;
* отвечать на вопросы по документу на естественном языке.

### 4. Нейросеть

Нейронка нужна не вместо правил, а поверх них:

* классификация типа документа;
* определение семестра по шаблону;
* извлечение слабоструктурированных признаков;
* анализ содержания, если структура сложная;
* помощь в генерации объяснений.

Правильная архитектура такая:

* **жёсткие требования** проверяются правилами из базы знаний;
* **нечёткие признаки** анализируются нейросетью;
* **объяснение и поиск по методичкам** даёт RAG.

## Как выглядит полный сценарий использования

### Для студента

1. Загружает документ
2. Запускает анализ
3. Получает:

   * тип документа;
   * предполагаемый семестр;
   * список нарушений;
   * рекомендации

### Для преподавателя

1. Загружает или открывает документ
2. Получает отчёт
3. Быстро видит:

   * соответствует ли работа шаблону;
   * какие правила нарушены;
   * насколько документ похож на требуемый формат

## Что должно быть в отчёте

Отчёт должен содержать:

* идентификацию документа;
* определённый тип;
* определённый семестр;
* список применённых правил;
* список нарушений;
* степень критичности;
* рекомендации;
* итог: соответствует / частично соответствует / не соответствует.

## Самая правильная формулировка идеи курсовой

Если кратко, ваша курсовая должна описывать такую логику:

> Пользователь загружает учебный документ. Система извлекает его текст и структуру, с помощью базы знаний и интеллектуальных модулей определяет тип документа и семестр, выбирает релевантные требования, проверяет документ на соответствие этим требованиям и формирует отчёт с найденными нарушениями и рекомендациями.

## В одном абзаце

Это должна быть система, где пользователь загружает PDF или DOCX, система извлекает текст и структуру, определяет вид работы и семестр, подбирает из базы знаний нужные правила, проверяет документ по структуре и оформлению, фиксирует нарушения, объясняет их и выдаёт итоговый отчёт. База знаний хранит правила, ограничения, шаблоны и связи между типами документов, семестрами и требованиями, а нейросеть и RAG используются как вспомогательные модули для распознавания, интерпретации и более гибкого анализа. Основа проекта — именно база знаний, а не просто интерфейс или проверка файла. Это прямо соответствует цели и задачам записки.
